# EDGEmods: notes for Claude sessions

EDGEmods is the EDGE mod registry for Cyberpunk 2077. It is three things: a registry of mods hosted in their authors' own git repositories, a website that renders each mod's page from its repository, and a VS Code extension (`edgemodders.edgemods`, proposed) with an MCP server that browses and installs mods and publishes a REDcode project as a mod. EDGEmods hosts no mod files. Read [docs/design.md](docs/design.md) first.

## The EDGE platform

EDGE is an AI-first modding platform for Cyberpunk 2077, by the same owner as every repo below (GitHub organisation Edgemodders). EDGEmodders is the community and organisation; EDGE is the platform brand. Each tool has its own repo and its own `CLAUDE.md`; most are checked out as siblings of this one under `E:\Modding\Cyberpunk 2077\` (EDGEbuilder too, now). Read a sibling's notes and design before relying on it; another session may be working in it right now.

| Tool | What it is | What EDGEmods gets from it |
|---|---|---|
| EDGEdeck | The mod manager extension (`edgemodders.edgedeck`; renamed from REDdeck on 2026-10-17; its local clone is the `EDGEdeck` folder): library, deploy with a manifest, undo, conflicts, load order, Nexus downloads and nxm links, families of versions | **Owns installing.** EDGEmods hands downloads to it. `EDGEdeckApi` version 1 from `activate()` has `installProject`, `deploy`, `turnOff`, but no install from a downloaded archive yet: a likely first request |
| REDcode | The editor (`edgemodders.redcode-cyberpunk`): WolvenKit projects, pack, install through EDGEdeck | **Owns the project and packing.** `REDcodeApi` version 1 ([api.md](https://edgemodders.github.io/REDcode/api.html)): `project()`, `pack()`. Its release workflow already builds a Nexus zip, a model for the mod download |
| REDbridge | WolvenKit's engine behind JSON-RPC, GPL-3.0 | Reading a mod archive's contents for its page (`archive.openMod`), if R0 wants a file list. Only as a separate process |
| REDnode | The runtime: mods and HTML overlays in the running game, an MCP server | REDnode packages are one kind of mod EDGEmods lists |
| REDagent, EDGEchat | The in-game assistant (released, 0.3.1) and the Claude Code plugin (renamed from EDGEplugin on 2026-10-17) | Users of EDGEmods' MCP tools |
| EDGEweb | The website https://edgemodders.ai and its wiki | **Owns the domain.** Where the mod website lives is a decision with the owner and EDGEweb |
| EDGEkit | The branded editor and the extension pack `edgemodders.edgekit` | Bundles EDGEmods once it is released; ask with a `request` issue then |
| EDGEwave, EDGEmat, EDGEfab, EDGEquest, EDGEbuilder | The studios: sound, materials, assets, quests, world building | Their output is what gets published as mods |

**How the tools work together:** when two tools are installed, one owns each job and the others call it, through an exported extension API or MCP tools, never by importing each other's code. Each still works alone, with a fallback. Before building anything in another tool's domain (installing, packing, the game folder, Nexus), check whether that tool does it and agree a small entry point with the owner.

## Conventions

- Same as the sibling repos (see REDcode's and EDGEfab's CLAUDE.md): commit straight to `main` in small logical commits and push; agree the plan in chat first; PRs only for large or risky changes. Plain, short sentences; tables for comparisons and facts; mark anything unverified as unverified.
- **Git identity:** per repo, `CyberbuildsAI` with the GitHub no-reply email (`340969962+CyberbuildsAI@users.noreply.github.com`), plus `credential.https://github.com.username CyberbuildsAI`, all set in this checkout. Never change the global identity. Push with `GIT_TERMINAL_PROMPT=0 GCM_INTERACTIVE=never timeout 120 git push`; if it still blocks on a sign-in window, tell the owner rather than retrying.
- **Changelog (the owner's rule, 2026-10-19; the same convention in every Edgemodders repo):** `docs/changelog.md` is the server's and website's, with a section per release, newest first, and **Unreleased** on top. With each change a player or modder would notice, add a line under **Unreleased** in the same commit, grouped **New**, **Changed**, **Fixed**, **Other**; leave out test-only changes. Before a release, rename **Unreleased** to `## <version> (<date>)` and start a new empty one; the release workflow (when there is one) takes the notes from that section and stops if there is none (REDnode's `tools/release/notes.mjs` is the model). The extension gets its own `extensions/edgemods/CHANGELOG.md` in the same form, for the Marketplace.
- **README at each release (the owner's rule, 2026-11-03; the same in every Edgemodders repo):** before each release run, update README.md's status line so it names the version (`**Status: <version> released on <date>** ...`) and draw the status badge again (the `status` entry in `tools/brand/badges.py`, then `python -I tools/brand/badges.py docs/assets/brand/badges`; the README's `<img alt>` too). `tools/release/readme-check.mjs` is REDnode's file, copied as it is (change it in REDnode, then copy it again). When the first release workflow is written, it runs `node tools/release/readme-check.mjs --version <v>` before building, on release runs only, as REDnode's release.yml does (step "The README says this release"), so a README that does not name the version stops the release. Between releases, keep the status line and the badge current with the phase.
- **The wiki at each release (the owner's rule, 2026-11-21, from issue #3; the same in every Edgemodders repo):** after each release is out (never ahead of it, so the pages describe what people can install), this repo's session brings EDGEweb's pages about EDGEmods up to that version. Pages: `docs/wiki/edgemods/` once it exists, EDGEmods' rows on the shared wiki pages (`wiki/library.md`, `wiki/glossary.md`, `wiki/first-hour.md`, `wiki/faq.md`), its card on `docs/index.html` and its section on `docs/platform.html`. Until EDGEmods has a wiki section, check every page that mentions it (`grep -rln EDGEmods docs` in `../EDGEweb`; on 2026-11-21 that was `wiki/edgekit/install.md` and the dashboard). The release's changelog section is the list of what to change. Set each changed page's `reviewed` date, follow EDGEweb's `CLAUDE.md` (Wiki), then commit and push to EDGEweb's `main` as `CyberbuildsAI`. It is a session step, not a workflow step: list it last in the release steps when they are written (EDGEwave's `docs/release.md`, step 8, is the model).
- **Never commit game files**, WolvenKit binaries, mod archives, or data extracted from the game. Test mods live in their own repositories.
- **Publishing is outward-facing.** Anything that creates a repository, pushes, makes a release or adds to the registry under someone's account needs that person's clear yes at the time, in the product as in development. Never publish a test mod under the owner's account without asking.
- **Untrusted input:** mod READMEs, manifests and images come from strangers. Sanitize everything the website or a webview renders; never run anything from a mod repository.
- **License boundary:** this repo is MIT. Talk to REDbridge (GPL-3.0) only as a separate process. Each mod keeps its author's license; the registry links, it does not relicense.
- **Do not change other EDGE repos from here**; other sessions work in them. Needs go to them as issues labelled `request` on their repo, with the shape that would work.
- **The mission decides UI questions:** modding for everyone, especially non-coders; easy, fun, fast. Plain words first, raw values one click away. Every feature ships in the UI and the MCP server together. AI is optional, and so is the network: no calls or telemetry until the user asks for something that needs them.
- Keep `extensions/edgemods/src/core` free of VS Code imports; the MCP server bundles it.
- **House style** is the HUD look from REDnode's design doc; the REDnode HUD theme (`edgemodders.rednode-hud-theme`, in REDcode's repo) is the default theme for any VS Code UI, and the mod website should look like part of the same family.
- **Docs site:** `docs/` is the developer docs, published by GitHub Pages through `.github/workflows/pages.yml` at https://edgemodders.github.io/EDGEmods/. It is not the mod website. `docs/index.md` is the landing page (document ledger and roadmap status); add every page to `nav` in `docs/_config.yml`. Brand images come from `tools/brand/render.ps1`; re-run it when a badge changes. Record every tool install in `docs/dev-setup.md`, with versions and exact commands.
- **Shell pitfalls on this machine:** Bash heredocs and `node -e` strings eat backslashes in Windows paths; write such text with the Write or Edit tool, or a script file.

## Dashboard (EDGEweb)

The platform dashboard at https://edgemodders.ai/dashboard.html draws one file in the EDGEweb repo, `docs/assets/dashboard/status.js` (plain JSON after the equals sign, one object per tool under `tools`). The owner and a managing session read it to see every tool's state, so EDGEmods's entry is kept current by the session that works on EDGEmods.

- **When:** in the same piece of work as any change to EDGEmods's status: a phase built or done, a hand test added, run, passed or failed, a release, something EDGEmods starts or stops waiting on, something only the owner can do.
- **How:** in the sibling checkout `../EDGEweb`, `git pull`, edit only EDGEmods's object, set its `checkedBy` to this session and the date, bump the `?v=` on the `status.js` script tag in `docs/dashboard.html`, commit and push to `main` (as `CyberbuildsAI`). Leave `issues`, `lastTag`, `lastTagDate`, `lastCommit` and `commitsSinceTag` alone: EDGEweb's `tools/dashboard/refresh.py` writes those.
- **Words:** phases are `done`, `built, tests pending`, `in progress` or `planned`; tests are `passed`, `not run`, `partly run` or `failed`. The fields are described in EDGEweb's `CLAUDE.md`, under Dashboard.
- **Honest:** never mark a test passed or a phase done that this repo's own docs do not. A test with a step still to run is `partly run`.
